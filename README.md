# poc_databricks_updated

The 'poc_databricks_updated' project was generated by using the default-python template.

* `src/`: Python source code for this project, one folder per flow.
* `resources/`:  Resource configurations (jobs, pipelines, dashboard, alerts)
* `checks/`: DQX rule files, one per Silver table.
* `data/`: the input files, in the folder layout the flows expect. See below.
* `docs/`: the exercise, the data model, the ingestion plan, and
  [TABLES.md](docs/TABLES.md) — every object the flows build, by layer.
* `flows/flows/`: the seven flow requirement documents.
* `scripts/`: [first_run.sh](scripts/first_run.sh), which deploys the bundle and
  runs every flow in dependency order on a workspace where the tables do not
  exist yet. See [First run](#first-run).

Each flow has its own README under `src/flow0*/` covering what it builds, its job
and trigger, the quality gate, the decisions not specified by the requirements,
and what to expect from a run.


## Input data layout

The flows read from a Unity Catalog volume, not from this repo. `data/` holds the
files to upload and **the folder structure is part of the contract** — every load
reads a folder and selects within it by file name, so a file in the wrong place is
not found.

The sources arrived as one flat directory. They are grouped here by domain, which
is what the loads expect:

```
data/
  currencies_exchanges/   currencies.csv, exchange_rates_historical.csv
  customer_data/          customers.csv, customers_dirty.csv
  orders/                 orders.parquet, orders_stream.parquet,
                          orders_schema_change.parquet, order_status_changes.parquet,
                          orders_stream_bad_data.parquet (deliberately invalid)
  products_excel/         products_excel.xlsx
  invoices/               INV-0001.pdf … INV-0030.pdf
  sellers_delta/          a Delta table directory, read as-is
```

The volume has its own `data/` folder, so this directory maps onto it directly:

| here | in the volume |
|---|---|
| `data/` | `/Volumes/<catalog>/<bronze_schema>/input_data/data/` |
| `data/orders/orders.parquet` | `/Volumes/.../input_data/data/orders/orders.parquet` |

Upload the `data` folder into the volume and the paths line up. The volume and
the schemas are created by the bundle, so deploy before uploading.

A folder groups a domain rather than a single table: `orders/` feeds both
`bronze_order` and `bronze_order_status_changes`, and each load applies its own
`pathGlobFilter`. `currencies_exchanges/` feeds `bronze_currency` and the historical
rate view, and those two name their file exactly rather than globbing.

Three of the folders are also file arrival trigger paths — `products_excel/`,
`customer_data/` and `invoices/` — so a file uploaded flat instead of into its
folder means the trigger never fires **and** the load reports success having read
nothing. Auto Loader finds no files and raises nothing, so an unloaded source
looks exactly like a run with no new deliveries. That is why the layout is worth
getting right before the first run rather than after.


## First run

[scripts/first_run.sh](scripts/first_run.sh) does all of this, in order, and
handles the two jobs that cannot be created until the tables they watch exist:

```bash
scripts/first_run.sh dev
```

The steps below are what it does and why, for reading or for running by hand.

The order matters, because four quality gates reference tables another flow
builds. `silver_order`'s gate reads `silver_customer`, `bronze_product` and
`bronze_currency`; `silver_invoice`'s and the status history's read
`silver_order`; `silver_exchange_rate`'s and `silver_seller`'s read
`bronze_currency`.

**1.** Deploy. This creates the schemas and the volume, so it comes before the
upload. The catalog itself is not a bundle resource and has to exist already.

```bash
databricks bundle deploy -t dev
```

On a workspace where the tables do not exist yet, two jobs fail to be created
and the rest succeed. A table update trigger is validated when the job is
created, so `build_silver_exchange_rate` cannot be created before
`bronze_currency` exists, nor `build_gold_marts` before the seven star-schema
tables do. Flow 01 requires that trigger, so this is not avoidable — the two
jobs are created by the later deploys in steps 5 and 6.

**2.** Upload the `data` folder into the volume, folders and all. The repo
already holds the layout the flows expect, so this is a straight copy with
nothing to rearrange.

Three jobs have a file arrival trigger on folders this upload fills:
`load_bronze_product`, `load_bronze_customer` and `load_bronze_invoice`. They
start themselves if the job already existed when the files landed. On a rebuild,
where the data is already in the volume and no file arrives, nothing starts them
and they are run by hand — which is what the script does, and what steps 3 and 4
below assume.

**`load_bronze_invoice` is expected to fail when the upload starts it.** Its
quality gate checks each invoice against `silver_order`, which does not exist
until step 4. That first run is the one failure a clean rebuild is supposed to
have; the run in step 4 succeeds, and costs almost nothing because the PDFs are
already parsed. So on a from-zero path those three jobs appear twice in the run
history, one of them failed the first time, and all of them succeeded in the
end.

**3.** Load the four reference and dimension sources. Order matters from here:
`silver_order`'s gate reads `silver_customer`, `bronze_product` and
`bronze_currency`, and fails loudly if any of them is empty.

```bash
databricks bundle run load_bronze_currency -t dev
databricks bundle run load_bronze_product -t dev
databricks bundle run load_bronze_customer -t dev
databricks bundle run load_bronze_seller -t dev
```

The seller job is the one Bronze load with a schedule rather than a trigger,
because nothing pushes to a Delta folder; running it by hand is the alternative
to waiting for 02:00 UTC.

**4.** Load the orders, then everything that reads `silver_order`.

`load_historical=true` is required on a first run and is **not** the default. It
is what loads `orders.parquet`, the thirty-order backfill; without it a condition
task skips that step and Bronze gets only the two replay deliveries, which carry
sixteen rows for eight orders.

```bash
databricks bundle run load_order -t dev --params load_historical=true
databricks bundle run load_order_status -t dev
databricks bundle run load_bronze_invoice -t dev
```

The status history and the invoice gate both read `silver_order`, so they come
after it rather than alongside. Later runs need no parameter: the default is
`false`, so a routine run picks up the stream and schema-change deliveries
without trying to append the backfill again.

**5.** Deploy again. `bronze_currency` exists now, so the job that watches it
can be created, and then run it. It calls the NBP API and publishes
`fact_exchange_rate`, the seventh star-schema table.

```bash
databricks bundle deploy -t dev
databricks bundle run build_silver_exchange_rate -t dev
```

**6.** Deploy a third time. All seven tables the mart job watches exist now, so
it can be created. Running it builds the four marts, checks them, refreshes the
dashboard and evaluates the two alerts.

```bash
databricks bundle deploy -t dev
databricks bundle run build_gold_marts -t dev
```

From here nothing needs starting by hand: the mart job's trigger fires five
minutes after any Gold table changes.

**Expect both alerts to be triggered, and an email for each. Both are
correct.** `no_orders_today` fires because every order is dated January 2026, so
`current_date()` has none — it is a freshness check, and the data genuinely is
stale. `quarantine_spike` fires because `orders_stream_bad_data.parquet` is in
the repo so that a run produces a real quarantine row, which is what EXERCISE
deliverable 6 asks to show.

A triggered alert does not fail its task: the documented behaviour is
"Succeeded … regardless of whether the alert condition was triggered or not". So
a healthy run is a green job with two red alerts and two notifications. Check the
junk folder if only one arrives.

Three jobs have no trigger and are always started by hand:
`load_bronze_currency`, `load_order` and `load_order_status`. Flow 01 asks for
the first to be manual — "someone approves a currency change on purpose" — and
flows 03 to 05 specify no trigger at all, so the order jobs read fixed files
rather than a folder that keeps receiving deliveries.

### When a gate's reference table is missing

The gates do not behave alike, which is worth knowing before reading a failed
run.

`silver_order`'s gate fails loudly, through `require_references`: an empty
`silver_customer`, `bronze_product` or `bronze_currency` stops the task. Every
other gate treats an empty reference as every row failing a foreign key, which
is a warning — so the rows still land in Silver, each with a quarantine entry,
and the run reports success.

The split follows the criticality of the foreign keys, not the number of them.
`silver_order` is the only gate with a foreign key marked `error`; the other
eight, across all the rule files, are warnings. A warning does not reject the
row, so an empty reference there flags everything and costs no data. An error
does reject, and `silver_order` then has nothing valid left to write — its merge
deletes the rows that are no longer in the source, so an empty
`bronze_currency` would empty the Silver table, and `fact_order` is a full
overwrite from it. A successful run would leave both empty.

So the guard belongs wherever a foreign key is an error, and today that is one
gate. Promoting another gate's foreign key to `error` is what would call for it
there too.

## Platform constraints that shaped the design

The project runs on Databricks Free Edition, which is serverless-only. Five of
its limits are visible in the architecture rather than in a workaround, so they
are worth knowing before reading a design decision and wondering why.

| Constraint | What the project does instead | Explained in |
|---|---|---|
| `append_flow`'s `depends_on` is Public Preview and cannot be enabled for serverless | Flow 05's three Bronze loads are notebook tasks in a job, ordered with the job's own `depends_on`, rather than flows inside one pipeline | [flow 05](src/flow05/README.md) |
| Serverless supports no Maven coordinates, no JAR libraries in notebooks and no third-party Spark data sources, and there is no classic compute to fall back to | The Excel workbook is read with the runtime's native `cloudFiles.format = "excel"` rather than `spark-excel` | [flow 02](src/flow02/README.md) |
| No external location over cloud storage | `bronze_seller` is a managed table, and the Delta folder in the volume is read in place with `delta.'<path>'`. The external table the flow document suggests practising on is not possible | [flow 02](src/flow02/README.md) |
| One SQL warehouse, 2X-Small | The dashboard and both alert tasks resolve `Serverless Starter Warehouse` by name, which is the only one such an account has | [flow 07](src/flow07/README.md) |
| At most five concurrent job tasks per account | Every job graph stays well inside that. The widest, `build_gold_marts`, runs two tasks at once | [flow 07](src/flow07/README.md) |

One more applies without changing anything: Free Edition allows one active
pipeline per pipeline type, and the project defines exactly one —
`order_status_history`, which exists because `AUTO CDC` is pipeline-only. A
second pipeline would not fit.

The first of these is the one with a consequence worth stating plainly. Ordering
the three order deliveries is what makes the `sales_channel` widening a recorded
schema change: unordered, whichever delivery commits first decides whether
`bronze_order` ever lacked the column, so the widening might never appear in the
table's history at all. Flow 05 asks for the widening to be demonstrated, and
the job's task chain is what guarantees it.

## Getting started

Choose how you want to work on this project:

(a) Directly in your Databricks workspace, see
    https://docs.databricks.com/dev-tools/bundles/workspace.

(b) Locally with an IDE like Cursor or VS Code, see
    https://docs.databricks.com/dev-tools/vscode-ext.html.

(c) With command line tools, see https://docs.databricks.com/dev-tools/cli/databricks-cli.html

If you're developing with an IDE, dependencies for this project should be installed using uv:

*  Make sure you have the UV package manager installed.
   It's an alternative to tools like pip: https://docs.astral.sh/uv/getting-started/installation/.
*  Run `uv sync --dev` to install the project's dependencies.



# Using this project using the CLI

The Databricks workspace and IDE extensions provide a graphical interface for working
with this project. It's also possible to interact with it directly using the CLI:

1. Authenticate to your Databricks workspace, if you have not done so already:
    ```
    $ databricks configure
    ```

2. To deploy a development copy of this project, type:
    ```
    $ databricks bundle deploy --target dev
    ```
    (Note that "dev" is the default target, so the `--target` parameter
    is optional here.)

    This deploys everything that's defined for this project.

3. Similarly, to deploy a production copy, type:
   ```
   $ databricks bundle deploy --target prod
   ```

4. To run a job or pipeline, use the "run" command:
   ```
   $ databricks bundle run
   ```

5. To tear everything down again, use the "destroy" command. It removes the
   schemas and the volume as well, so the uploaded input files go with them:
   ```
   $ databricks bundle destroy --target dev
   ```
